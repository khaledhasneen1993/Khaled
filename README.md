# Khaled 4.1.0 — Binance USDT-M Futures Demo

نسخة المصدر المرجعية على `main`. الإشارة والتحجيم والخروج مشتركة بين Paper وDemo. **مسار التشغيل المعتمد للتداول هو `run_demo.py` على Demo فقط؛ Mainnet مرفوض وغير معتمد.** الإصدار4.1.0 يضيف استعادة الحالة والشبكة ومراقبة العملية وأوضاع Kill Switch؛ منطق الدخول والرافعة وTP/SL كما في4.0.2. التحقق الممتد72ساعة ما زال معلقًا؛ هذه ليست شهادة جاهزية لأسبوعين.

## الاستقرار في4.1.0

| البيئة | Kill Switch | WS / أخطاء API خلال دقيقة / سبريد / DD / خسائر |
|---|---|---|
| Paper وBinance Demo | observe: سجل وتنبيه فقط |300ث /30 /15× /15% /10 |
| testnet مستقل في طبقة السياسة | soft: منع دخول600ث ثم استئناف بعد زوال السبب ومصالحة ناجحة |120ث /15 /10× /10% /6 |
| Mainnet في طبقة الحماية | hard مفروض مهما كان إعداد mode |60ث /10 /8× /5% /4 |

اسم تشغيل Demo في المشروع هو `testnet`، لكن عنوان `demo-fapi.binance.com` يصنفه **demo** ويُلزمه observe. Mainnet يبقى مرفوضًا في المشغل المعتمد؛ وجود سياسة hard لا يفتح تشغيله.

observe لا ينفذ تسطيح الحساب أو وقف الدخول بسبب عتبات Kill Switch. تبقى شروط سلامة التنفيذ نافذة: لا أمر بلا WAL ناجح، ولا دخول قبل المصالحة، ولا إعادة POST غامض، ولا إعادة دخول رمز بإدارة معلقة. فشل حماية رمز بعينه يستمر بمعالجته الحالية دون تغيير TP/SL. فشل التخزين يمنع الدخول ويُعاد فحصه والمصالحة قبل السماح به؛ لا يرسل أوامر مالية بلا كتابة متينة، حتى عند امتلاء القرص.

WAL (`runtime/testnet/journal.wal`) يسجل قبل تغيير الملفات وقبل POST/DELETE المالي. الاستعادة تعيد **الحقائق** ثم تستعلم بنفس معرّف الأمر؛ لا تعيد إرسال أوامر من السجل. يُتجاهل آخر سطر ممزق فقط، والتلف الداخلي يرفض التشغيل. ضغط السجل يحفظ آخر snapshot لكل ملف. لا تحذف WAL أو تعدّل JSON يدويًا لتصفير الحالة. الاحتفاظ بالحقائق في WAL لا يعوض تلف القرص كله أو انقطاعه.

SIGINT/SIGTERM يمنع الدخول، ويمهل الإجراء الجاري حتى ثانيتين، ثم يحفظ ويغلق الاتصالات. **لا يغلق المراكز ولا يلغي أوامر حمايتها**. إذا انتهت المهلة أثناء أمر لم يُحسم، تُستعاد نيته وتُصالح عند البدء؛ لا ندعي وجود وقف مؤكد لأمر لم يصل تأكيده. لا تصفّر session guard تلقائيًا إلا بعد حفظ الإغلاق الهادئ. Restart بعد crash على Demo يصالح ويتبنى التنفيذ ويحميه قبل الدخول؛ hard يحتفظ بمراجعة الجلسة غير النظيفة.

الـCircuit Breaker يوقف طلبات GET مؤقتًا بعد30فشل، ثم يسمح باختبار واحد بعد30ث. أوامر الحماية/الخفض الطارئ لا تُعطل بسببه، ولا تُعاد المحاولات المالية خارج مسار النيات الدائم. WS يعاود الاتصال مع backoff وعشوائية حتى60ث؛ بلوغ مهلة الانقطاع يسجل في observe ويستمر بالمحاولة. لا تُستخدم أسعار قديمة للإشارات: تبقى فحوص حداثة أحداث الشموع كما هي.

### Termux: إعادة تشغيل ومراقبة مستقلة

بعد إعداد المفاتيح وTelegram محليًا والـpreflight الحالي، يمكن التشغيل المباشر `python -u run_demo.py`، أو مشرف إعادة التشغيل:

```bash
python -u tools/supervise_demo.py
```

وفي جلسة Termux ثانية، بنفس متغيرات Telegram:

```bash
python -u tools/watch_health.py
```

يستعلم المراقب المستقل كل10ث، وينبه عند تغير healthy/degraded/offline. وصول Telegram خلال30ث يعتمد على توفر الإنترنت وTelegram وعمل المراقب؛ لا يستطيع الهاتف المطفأ إرسال تنبيه. استخدم `termux-wake-lock` وأزل قيود البطارية محليًا. systemd غير متاح داخل Termux المعتاد؛ لا تشغّل مشرفين على الحساب نفسه. Ctrl+C في **جلسة المشرف** يوقفه وابنه؛ إيقاف الابن وحده يعيد تشغيله.

```bash
python tools/status.py
python tools/tail_events.py --follow
```

`http://127.0.0.1:8080/health` محلي ويقرأ حالة الذاكرة فقط، دون Binance. stdout بصيغة JSON، والأحداث الدائمة بصيغة JSONL. فحص موارد العملية مستقل عن انقطاع السوق؛ تجاوز1.5GB أو10000FD أو heartbeat معلق يخرج برمز خطأ ليتولى المشرف الإعادة. تحقق ميدانيًا من الذاكرة والملفات خلال اختبار72ساعة؛ لم يُثبت حد أسبوعين بعد.

### Linux مع systemd

ضع النسخة في `/home/khaled/Khaled`، وأنشئ `.venv` و`.env` بصلاحية0600، ثم:

```bash
sudo bash deploy/install.sh
sudo systemctl start khaled-health khaled-bot
journalctl -u khaled-bot -f
```

التثبيت يفعل الخدمات للبدء عند إقلاع الجهاز التالي، **ولا يبدأ تداولًا فورًا**. `Restart=always` مع تعطيل start-rate-limit يسمح بالتعافي بعد انقطاع طويل؛ حد خمس إعادات كان سيترك الخدمة متوقفة. stdout/stderr إلى journald لتدوير سليم؛ سجلات التشغيل لها logrotate منفصل مع copytruncate. لا يوجد أمر reload غير مدعوم.

بعد تشغيل Demo والمراقب على جهاز مستقر، شغّل في جلسة ثالثة:


الأداة لا تبدأ التداول؛ تجمع HTTP latency والذاكرة وFD وuptime وإعادات التشغيل والصفقات وPnL وأحداث observe. تحفظ `runtime/testnet/soak_report.json` و`soak_samples.jsonl`. التوقف المبكر ينتج pending، والانقطاع أو إعادة التشغيل أو تجاوز الموارد/زمن100ms ينتج failed. لا يُعتمد passed قبل مرور72ساعة فعلية. قياس هذه الأداة لا يثبت وحده انعدام كل صفقة مفقودة؛ راجع دفتر Binance ومصالحة الأوامر مع التقرير. اختبارات الفوضى غير المتصلة لا تعادل اختبار72ساعة أو اختبار systemd على الخادم.

## لماذا الهامش الفعلي أقل من10%؟

وقف8% عند هامش10% ورافعة10× يعرّض نحو8% من equity للخسارة قبل الرسوم؛ لذلك لا يمكن الجمع بين هذه الكمية وسقف مخاطرة2.5%. يُحافظ على الوقف ويُخفّض الحجم، بدل تضييق الوقف إلى مستويات ATR القديمة.

للسعر P، وequity الحساب E، والرافعة L، ورسوم f:

```text
Q_target = E × 0.10 × L / P
Q_risk = E × 0.025 / [P × 1.003 × (0.08 + f × 2.08)]
Q = round_down(min(Q_target, Q_risk))
margin = Q × actual_fill_price / L
```

التقدير محافظ لكلفة وقف البيع ورسومه ويضيف احتياط دخول30bps. مع رسوم0.0005 يكون الهامش نحو3.1% من equity عند10×. لا يزيد الحجم لتجاوز minQty/minNotional، ولا يقسّم الدخول لتجاوز maxQty. يُسجل الهامش المستهدف والفعلي والميزانية والرافعة.

لا يُخفض الحجم وحده مسافة التصفية في الهامش المعزول؛ لذلك اعتمد المشغّل10× بدل الرافعة القصوى. تستخدم حدود Binance الفعلية وMMR وخصم الصيانة، وتُرفض الصفقة إذا لم يقع وقف8% قبل حد التصفية مع buffer0.003. بعد التنفيذ تُفحص التصفية الفعلية؛ فشل الحماية يطلق الطوارئ. لا يوجد ضمان للخسارة القصوى أثناء فجوات السعر أو الانزلاق أو انقطاع الخدمة.

## الإيقاف المؤقت

اضغط `Ctrl+C` في جلسة تشغيل البوت، وانتظر عودة موجه الأوامر. يحاول البرنامج الإغلاق الآمن وحفظ القفل؛ تحقق مباشرة من Binance Demo أن المراكز والأوامر العادية وAlgo كلها صفر. إذا بقي مركز، احتفظ بحمايته حتى تغلقه من Binance ثم راجع الأوامر المتبقية. لا تشغّل نسخة ثانية إذا علقت العملية.

احتفظ بـ`runtime` والسجلات؛ لا تصفّر القفل أو تعاود التشغيل وأنت تريد إبقاء التداول متوقفًا. الوكيل لا يستطيع إيقاف جلسة Termux على هاتفك عن بُعد.

## تحديث التثبيت الحالي والحفاظ على التاريخ

حالة4.0.0 و4.0.1 و4.0.2 متوافقة مع4.1.0؛ لا تحتاج ترقية السياسة مرة ثانية أو حذف runtime أو إعادة القفل لمجرد هذا التحديث. أداة الترقية أدناه لازمة عند الانتقال من سياسة3.2.x القديمة.

داخل حاوية Ubuntu التي تحتوي التثبيت الصحيح؛ في حالة المشغّل السابقة كانت `cascade-ubuntu`. اسم المجلد القديم مثل `Khaled-3.2.1` لا يحدد إصدار المصدر، ولا يلزم تغييره أو إعادة إنشاء venv.

بعد إيقاف العملية، من مجلد التثبيت المستقل الذي يحتوي **أحدث** runtime:

```bash
source .venv/bin/activate
flock -n -E 75 runtime/testnet/account.lock git pull --ff-only
git log -1 --oneline
python tools/demo_preflight.py
```

رمز75 من flock يعني أن عملية لا تزال تمسك القفل. لا تستخدم `reset --hard` أو تنسخ حالة أقدم فوق الأحدث. تغيّر السياسة يجعل حالة3.2.x غير مطابقة لإعدادات4.x؛ لا تتجاوز هذا الرفض بحذف الحالة.

للانتقال من3.2.x فقط، اعرض معاينة الترقية أولًا:

```bash
python tools/upgrade_demo_policy.py
```

أداة الترقية تقرأ Binance بـGET فقط، وترفض أي مراكز أو أوامر أو تنفيذ/محاسبة معلقة محليًا أو بالبورصة. تعرض الإعدادات القديمة والجديدة وبصمة `preview_sha256` دون تعديل الحالة. بعد مراجعة المعاينة:

```bash
python tools/upgrade_demo_policy.py --apply --expected-sha256 البصمة_المعروضة
```

تحفظ الأداة نسخة محلية من الحالة قبل التعديل، وتغيّر لقطة إعدادات التشغيل فقط. تبقى الصفقات والقفل وعدادات المخاطرة وعلامة الجلسة والدفاتر والسجلات محفوظة. لا تعدّل أوامر Binance ولا تبدأ التداول أو تعيد قفل الأمان. إذا رفضت بسبب شيء معلق، راجع الاستعادة أولًا؛ لا تشغّل التداول لمجرد محاولة كشف الخطأ.

## تثبيت جديد داخل Ubuntu على Termux

استخدم مجلدًا منفصلًا؛ احتفظ بالتثبيت السابق وruntime. لا تشغّل تثبيتين على الحساب نفسه. إن كان للحساب تاريخ محلي قائم، فاحتفظ بأحدث حالة وانقلها تحت القفل بمراجعة واعية ثم استخدم أداة الترقية؛ لا تبدأ بسجل جديد لتجاوز الخسائر أو القفل.

باستخدام Python3.11 أو أحدث:

```bash
apt update
apt install -y git python3 python3-venv
mkdir -p ~/khaled-installations
cd ~/khaled-installations
git clone --branch main --single-branch https://github.com/khaledhasneen1993/Khaled.git Khaled-4.1.0
cd Khaled-4.1.0
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

## المصادقة والتنبيهات

دوّر أي مفتاح Demo سبق ظهوره في صورة إن لم تكن دوّرته. لا ترفع مفاتيح أو ملف RSA أو رموز Telegram إلى المحادثة أو Git أو baseline أو السجلات.

أدخل كل سطر بمفرده، ثم أدخل القيمة عندما ينتظر الطرفية الإدخال المخفي:

```bash
read -r -s -p 'Demo API key: ' BINANCE_API_KEY; export BINANCE_API_KEY; echo
read -r -s -p 'Telegram bot token: ' TELEGRAM_BOT_TOKEN; export TELEGRAM_BOT_TOKEN; echo
read -r -s -p 'Telegram chat ID: ' TELEGRAM_CHAT_ID; export TELEGRAM_CHAT_ID; echo
```

اختر طريقة واحدة فقط. RSA، بملف PKCS#8 مرتبط بالمفتاح العام المسجل في Binance Demo:

```bash
unset BINANCE_API_SECRET
export BINANCE_RSA_PRIVATE_KEY_PATH=/root/.binance-demo-keys/private.pem
chmod 600 "$BINANCE_RSA_PRIVATE_KEY_PATH"
```

أو HMAC:

```bash
unset BINANCE_RSA_PRIVATE_KEY_PATH
read -r -s -p 'Demo HMAC secret: ' BINANCE_API_SECRET; export BINANCE_API_SECRET; echo
```

أعد توفير المتغيرات في كل جلسة جديدة، أو احفظها محليًا خارج المستودع بصلاحية0600. Telegram إلزامي لتشغيل Demo، ويُختبر تسليم رسالة البدء قبل الدخول. الأحداث تشمل `trade_opened` و`trade_closed` و`kill_observe` و`kill_triggered` و`daily_report`. يتضمن الإغلاق الرمز والاتجاه والسبب وصافي PnL وequity.

## التنفيذ والحماية والاستعادة

تُحفظ النية ذريًا قبل POST بمعرّف ثابت؛ عند فقد الرد يُستعلم عن الأمر نفسه دون إعادة دخول عمياء. FILLED مستقل عن اكتمال userTrades. عند غياب سعر التنفيذ تُحفظ الكمية المؤكدة ويُستعاد avgPrice أو cumQuote/executedQty دون اختلاق سعر إشارة. المحاسبة الدقيقة تنتظر البيانات وتُعتمد مرة واحدة.

على Binance تُطلب حماية `STOP_MARKET` من Algo لكامل المركز. التريل يستبدل الوقف: إنشاء ثم تأكيد ثم حفظ البديل قبل إلغاء القديم. CONTRACT_PRICE هو المصدر الافتراضي لتفعيل الخروج، وMark يستخدم لقياس خطر التصفية؛ لا يُعد لمس الوقف وحده فشل حماية. تحفظ بيانات التريل وأفضل سعر والرافعة ومعرّفات الأوامر عبر الاستعادة. التريل يحرك STOP_MARKET من البرنامج؛ عند انقطاعه تبقى آخر حماية مؤكدة، ولا يُضمن توقيت تحديثها خلال تعطل الشبكة.

لا توجد سياسة جني ربح جزئي. لكن Binance قد ينفذ أمرًا كامل الكمية جزئيًا أو يتطلب سقف أمر السوق تجزئة إغلاق طارئ؛ تُحسم الأوامر السابقة وتُقرأ الكمية الحقيقية المتبقية قبل أي إغلاق لاحق. لا وعد exactly-once للشبكة، ولا حذف لمحاسبة تنفيذ جزئي حقيقي. فشل حماية رمز واحد يُعالج وفق المسار التالي؛ تبقى الحماية المتاحة محفوظة خلال الاستعادة.

بعد تعبئة الدخول، تُجرّب الحماية ثلاث مرات، بفاصل0.5 ثم1 ثانية، مع الاستعلام عن **نفس المعرّف** عند غموض الإرسال. بعد الرفض المؤكد فقط، يمكن تجربة STOP_MARKET عادي إذا أعلن exchangeInfo دعمه؛ لا يُعتمد إلا بعد GET يؤكد القبول والكمية والسعر والاتجاه وreduceOnly. انتقال Binance إلى Algo قد يجعل هذا البديل غير متاح؛ رفض−4120/−1116 لا يُعد حماية ولا يبرر تجاهل الفشل. لا يُرسل بديل أثناء وجود Algo ملتبس.

إذا استُنفدت المحاولات، يصدر `symbol_management_failed` حرج بسبب `entry_confirmed_management_failed`، ويُغلق **رمز الصفقة المعنية فقط** بأمر market مخفّض. لا يُغلق IDOL لمجرد فشل حماية AKE. يجري التحقق من أمر الإغلاق السابق والمركز الحقيقي قبل إعادة المحاولة، حتى ثلاث محاولات. إذا تعذر إثبات إغلاق آمن للرمز، يُصعّد إلى `symbol_emergency_close_failed` على الحساب. تبقى حمايات الحساب المستقلة، مثل التخزين غير الآمن أو غموض دخول غير محسوم أو خرق buffer التصفية الفعلي، وسياسة السحب العامة المختارة، نافذة.

بعد إغلاق مؤكد، تأخر إلغاء Algo لا يلغي حقيقة الإغلاق ولا يكرر المحاسبة. تتم ثلاث محاولات cancel/query؛ ثم تُحفظ مهمة `protection_retirement_pending` في `runtime/testnet/management_faults.json` وتُستعاد أثناء المراقبة وإعادة التشغيل، بفاصل5 ثوانٍ للمهمات المؤجلة. يظل الرمز المتأثر ممنوع الدخول حتى التسوية، مع مهلة600 ثانية بعد فشل إدارة الدخول. تبقى بيانات الاستراتيجية والتنفيذ والمحاسبة المعلقة محفوظة. الأمر البديل يُنشأ ويُؤكد ويُحفظ قبل إزالة السابق؛ أي إزالة غير محسومة تُحفظ للاستعادة.

يعرض preflight الحقول `pending_symbol_management` و`symbol_entry_cooldowns`. ترفض أداة reset وجود مهمات إدارة معلقة؛ لا تُحذف ملفات runtime أو السجلات لتجاوزها، ولا يعيد هذا التحديث قفل الأمان العام تلقائيًا. الاستعادة الآلية المذكورة جزء من المحرك بعد اجتياز بوابات البدء، ولا تتجاوز شرط مراجعة جلسة توقفت بصورة غير سليمة.

state معزول في `runtime/paper` و`runtime/testnet`. قفل Demo يمنع عمليتين داخل مجلد الحالة نفسه فقط. لا يعتمد البوت على الرصيد الورقي لتداول Demo. المصالحة لا تبدّل حقائق الدخول بكمية متبقية أو تغلق مركزًا سليمًا لمجرد فرق كمية داخل التسامح المضبوط. تبقى ملفات الاستراتيجية والدفاتر والرسوم والنتائج التاريخية محفوظة.

التشخيص يسجل المرحلة ومعرّفات الأمر ونوع الخطأ وHTTP وكود Binance وإجراء الاستعادة دون نصوص استثناءات أو URLs موقعة. أداة `python tools/monitor_read_probe.py` تكرر قراءات REST فقط، وليست اختبارًا للمراقب الكامل. السبب التاريخي المحدد لحادثة monitor_failure القديمة غير معروف لغياب الاستثناء الأصلي.
